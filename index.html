How it works

Four steps, three skills, one rule: the files win.

1 · Definespec-package
  • PRD with requirement ids
  • Acceptance tests (Gherkin)
  • Flow, screen and API contracts
GateRequirements link to AC ids
2 · Find what it toucheschange-impact
  • Existing requirements, screens, APIs, events, tests
  • Each link proposed as a question
GateYou confirm each link; confirmed tests are protected
3 · Design the buildtechnical-design
  • TRD, API and event fragments
  • Decision records, reuse scan
  • Depth: light · standard · full
GateApproved PRD; new libraries stop and ask you
4 · Buildyour agent
  • Tests committed failing (RED)
  • Implement until GREEN
  • Assertions never edited
GateDone = runner output, diffed against RED

First run asks six setup questions (where specs live, how approval works, design depth, test runner) and saves them to .willgt/skills.yaml. Each skill also works on its own.

The skills

What each one refuses to do is the point.

spec-package

An executable spec in your repo

  • Briefs carry a package path, never prose pasted into chat.
  • Done means the package's acceptance tests pass.
  • No backfilling screens nobody is changing.
# AC-PR-001
Scenario: reset link expires
  Given a reset link older than 30 minutes
  When it is opened
  Then the reset is refused
change-impact

See what a change breaks before it ships

  • Searches specs by id and term for related requirements, flows, APIs and tests.
  • Nothing is linked until you confirm it.
  • A protected test that fails is a bug, not a test to update.
affects: AC-LOGIN-004
related_test: auth/login.feature
status: confirmed
technical-design

A build design at the depth you choose

  • Refuses to start from a draft PRD.
  • New library or service: stops and lists options for you.
  • Never installs anything.
design_depth: standard
approval: pr-merge
new_technology: ask-human

Story

"If I add 2FA, what breaks?"

WillGT · October 20, 2026

This started as a chat with friends who also build software for a living.

I told them the question I can finally ask an AI agent before any code is written: "If I add two-factor authentication, what happens to the rest of the project?" And it answers. It lists the login flow, the password reset emails, the session tests and the screens that assumed one step was enough. Then it asks me to confirm each one.

One friend said this sounded like BMAD, a method where AI agents first write PRDs and architecture documents, then write the specifications and implement them. He is right that it is close. BMAD is the process. What I built is my own implementation of one part of it, the part I kept finding missing.

Most AI tools I tried have agents that plan and design. But when you say "let's implement X", the agent starts writing code. Nobody stops to ask what X touches. That missing step is change impact, and it is where most of my bugs came from.

The second idea came from a simple question. Everyone writes unit tests. Who reads them to learn how a feature works? Usually nobody. When people bring an AI into a codebase, they tell it to read the code. I started telling it to read the tests, and the specs the tests come from. Tests describe what the system promises. Code describes how it happens to do it today.

Another friend laughed and said he spends his days arguing with people who want to exclude code from coverage. That is the same problem from the other side. If tests are the record of what a feature promises, skipping them is skipping the promise.

So the skills work in this order. First, define the feature as files: requirements with ids and acceptance tests in plain Gherkin. Second, run change impact: the AI searches the existing specs and tests for everything the feature may touch, and you confirm each link. Confirmed tests become protected. Third, design the build. Then the agent implements until the acceptance tests pass.

One thing it does not do: it does not write your test code. The skills define the acceptance tests in Gherkin and keep them honest. Turning them into runnable tests, and making them pass, is the build step.

The skills are open source. If you have ever watched an agent confidently break something it never looked at, try asking it what breaks first.

Launch post

Stop letting AI agents build from vague specs

WillGT · October 20, 2026

Ask an AI coding agent to "add password reset" and you will get code. It will look right. Whether it is right is a different question. Two things usually go wrong.

First, the agent builds from a loose description. Nobody wrote down what "done" means, so "done" becomes a claim: the agent says the tests pass, or the screen looks fine.

Second, nobody checks what the new feature touches. The login route, an existing email flow, a test that assumed the old behavior. The change lands, and something else breaks.

Today I am releasing WillGT Skills, three open-source skills for Claude Code that address both. They are Apache-2.0, created by WillGT, and install as a Claude Code plugin.

spec-package defines a feature as files in your repo: a PRD with requirement ids, acceptance tests in Gherkin, flows, screen contracts and API fragments. The acceptance tests are committed failing, by someone other than the implementer. The agent's job is to make them pass without editing their assertions. Done is the test output, not a statement.

change-impact searches your existing specs for requirements, screens, flows, APIs, events and tests the new feature may touch. It proposes each as a question to you. Nothing is linked until you confirm it. Confirmed tests become protected, and a protected test that fails is a bug.

technical-design writes the build design for an approved feature: a TRD, API and event fragments, decision records and a reuse scan, at the depth you set in setup. It refuses to start from a draft PRD. If the design needs a new library or service, it stops and asks you to choose between options. It does not install anything.

They chain: define, find what it touches, design the build, implement against failing tests. You can also use one alone.

Some limits. The skills are markdown instructions and templates, so they make no network calls of their own. Link finding is text and id matching, so a dependency that shares no term with the feature is found only if you name it. No CI enforces the package format yet.

Before release the plugin was validated, reviewed against Anthropic's skill checklist, tested with evals against a no-skill baseline, and security reviewed. With the skills, 31 of 32 test cases fully pass (change-impact 7/7, technical-design 7/7, spec-package 17/18); without them, Claude passes none.
