How it works

Four steps, three skills, one rule: the files win.

1 · Definespec-package
  • PRD with requirement ids
  • Acceptance tests (Gherkin)
  • Flow, screen and API contracts
GateRequirements link to AC ids
2 · Find what it toucheschange-impact
  • Existing requirements, screens, APIs, events, tests
  • Each link proposed as a question
GateYou confirm each link; confirmed tests are protected
3 · Design the buildtechnical-design
  • TRD, API and event fragments
  • Decision records, reuse scan
  • Depth: light · standard · full
GateApproved PRD; new libraries stop and ask you
4 · Buildyour agent
  • Tests committed failing (RED)
  • Implement until GREEN
  • Assertions never edited
GateDone = runner output, diffed against RED

First run asks six setup questions (where specs live, how approval works, design depth, test runner) and saves them to .willgt/skills.yaml. Each skill also works on its own.

The skills

What each one refuses to do is the point.

spec-package

An executable spec in your repo

  • Briefs carry a package path, never prose pasted into chat.
  • Done means the package's acceptance tests pass.
  • No backfilling screens nobody is changing.
# AC-PR-001
Scenario: reset link expires
  Given a reset link older than 30 minutes
  When it is opened
  Then the reset is refused
change-impact

See what a change breaks before it ships

  • Searches specs by id and term for related requirements, flows, APIs and tests.
  • Nothing is linked until you confirm it.
  • A protected test that fails is a bug, not a test to update.
affects: AC-LOGIN-004
related_test: auth/login.feature
status: confirmed
technical-design

A build design at the depth you choose

  • Refuses to start from a draft PRD.
  • New library or service: stops and lists options for you.
  • Never installs anything.
design_depth: standard
approval: pr-merge
new_technology: ask-human

The skills don't replace your orchestrator or its agents. They plug in as the steps those agents follow, write to files in your repo, and stop at two points for a human. Any agent that loads Agent Skills can use them; they ship as a Claude Code plugin.

It answered with what the change would touch:

  • the login flow
  • the password reset emails
  • the session tests
  • the screens that assumed one step was enough

Then it asked me to confirm each one.

That step is missing almost everywhere.

AI agents plan well. They design well. But say "implement X" and they start coding. Nobody asks what X touches.

A friend said this sounded like BMAD, where agents write PRDs and architecture, then specs, then code. Close. BMAD is the process. I built my own take on the step I kept finding missing.

The aha moment came from a simple question. Everyone writes unit tests. Who reads them?

We tell AI to read the code. I started telling it to read the tests.

Tests say what the system promises.
Code says how it does it today.Another friend spends his days arguing with people who want to exclude code from coverage. Same problem, other side.

So the skills work in four steps:

  1. Define the feature as files with acceptance tests
  2. Find what it touches and confirm each link
  3. Design the build
  4. Implement until the tests pass

For the 2FA feature, the files come out of templates like this:

spec/two-factor-auth/
  PRD.md            # requirements with ids; each one lists its AC ids
  ac.feature        # acceptance tests in Gherkin, committed failing
  flow.yaml         # screens it crosses; every edge has trigger, guard, effect
  DESIGN_BRIEF.md   # experience + constraints, for the human design pass
  TRD.md            # interfaces, data, failure behavior
  openapi.yaml      # one API path fragment, only if there is an endpoint
  event.schema.json # one event, only if the feature emits one
spec/screens/sign-in/
  screen.yaml       # the screen contract, catalog components only
.willgt/impact/
  two-factor-auth.impact.yaml   # what it touches: affects, related tests, each confirmed
.willgt/decisions/
  two-factor-auth.decisions.yaml # decision records (depth: full)

Why templates, and not "AI, write me a spec"?

  • The next agent can find itSame shape and the same ids every time. Change impact searches requirement ids, flow edges and AC ids. A free-form doc has nothing stable to match.
  • Everything is linkedA requirement must name its acceptance tests. A script fails the template if one is missing. Free text can claim coverage it doesn't have.
  • The hard questions are requiredEvery flow edge needs a trigger, a guard and an effect, even "no write". The design brief must have constraints. These are exactly what AI skips when it writes freely.
  • AI fills it in, you review a diffThe AI writes into a fixed structure instead of inventing one. You check small files against the template, and the next sprint doesn't reinvent the tables.

It does not write your test code. It defines the acceptance tests in Gherkin and keeps them honest; making them run and pass is the build step.

If you have watched an agent confidently break something it never looked at, ask it what breaks first.

Launch post

Stop letting AI agents build from vague specs

WillGT · October 20, 2026

Ask an AI agent to "add password reset" and you will get code. It will look right. Whether it is right is a different question.

"Done" is a claim

The agent builds from a loose description. Nobody wrote down what done means, so done becomes "the tests pass" or "the screen looks fine".

Nobody checks what it touches

The login route, an email flow, a test that assumed the old behavior. The change lands, and something else breaks.

Today I'm releasing WillGT Skills: three open-source skills for Claude Code that fix both.

  • spec-packageDefines the feature as files in your repo: requirements with ids, acceptance tests in Gherkin, flows, screen and API contracts. The tests are committed failing; the agent makes them pass without editing them.
  • change-impactFinds the requirements, screens, APIs, events and tests the feature may touch, and asks you about each one. Confirmed tests become protected.
  • technical-designWrites the build design at the depth you choose. Refuses a draft PRD. Stops and asks before any new library or service.

Define → find what it touches → design → build until the tests pass.Use the three together, or any one alone.

Limits, stated plainly
  • Markdown instructions and templates only. No network calls, no installs.
  • Link finding is text and id matching: a dependency that shares no term with the feature is found only if you name it.
  • No CI enforces the package format yet.
